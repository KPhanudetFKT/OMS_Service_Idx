POST /payments/charges · /webhook/:provider

Blocks on a synchronous external gateway round-trip (Omise / TTB / KTB / KBank) on the request path, then can call back into order to void/cancel.

N+1 to product: one goroutine + one product API call per brand on the post, unbounded by brand count.

#5

Sequential N+1: one Mongo read (+ any post enrichment) per post in the page layout, looped one-by-one.

#6
POST /shopping-cart/validate

Highest cart read fan-out: product (parallel chunks) + promotion ×2 + delivery slot + ~6 order-table reads + MSSQL restaurant.

F

Second hop — what each downstream calls next

where the request chain ends

The chains are shallow — now fully traced. Every second-hop service either terminates at a datastore or fans out to exactly one external dependency; none call another internal Freshket microservice (except promotion → product). Three things to know:

  • promotion → product is the one genuine internal third hop: validating a promotion calls back into product /skus (chunked-parallel). With product→promotion enrichment, order↔product↔promotion form a small cross-call cluster — no infinite cycle (different operations), but a shared latency surface.
  • HRMS → Auth0 (not a DB): staff identity / permissions are cache-aside over Auth0 (Redis-fronted). So every content /admin/* request ultimately depends on Auth0 being up.
  • Legacy MSSQL is the convergence point. order, payment, orderadapter and customer all read it directly (in-process GORM / ACL, not over HTTP). It's the most depended-on single resource in this slice.

Correction to hop 1: the order "buyer-authorize" edge labelled oms-api actually targets fk-web-host (a separate legacy MVC web app), not the oms-api service.
